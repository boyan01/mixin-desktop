# Mobile feature parity

Target: the base client (`mixin-bot-sdk`, `mixin_desktop_core`, `mixin_desktop_api`, `nsh`, `mixin_desktop_headless`) covers the features of the official Android, iOS, and Flutter desktop apps. [parity.md](parity.md) tracks the NSH UI against the Flutter desktop app by its own feature IDs.

References:

- `MixinNetwork/android-app` at `5a22160` (2026-11-10)
- `MixinNetwork/ios-app` at `9ef0a03` (2026-11-10)
- `MixinNetwork/flutter-app` at `225c621f` (2026-11-10)

The base client stays general. Assistant policy, such as which groups or people are accepted or may be messaged, belongs in a layer above it and is out of scope here.

## How to read this document

This is a source audit. Nothing was built, run, or exercised against a live account, so **Done means the code is located and wired, not that it was tested**. Server behaviour is unverified wherever a row compares request bodies. Windows and Linux are unverified.

| Status | Meaning |
| --- | --- |
| Done | A located implementation reachable through the runtime or API |
| Partial | Implemented in part; the cell says what is missing |
| Missing | No implementation found; the evidence cell says what was searched |

Android, iOS, and Flutter paths are relative to their repository, Fork paths to this repository. `not found` means the code was searched and nothing was located.

The Status column describes this repository only. The Flutter column does not change it. Text after the Flutter paths says what is missing when the Flutter code covers only part of a row.

Each Flutter `not found` cell lists its keywords. Each keyword is a case-insensitive substring search of the Dart and Drift files under `lib/`, without `lib/generated/`, and has no match. The search does not include the `mixin_bot_sdk_dart` package, so an API method that only the package defines is `not found`.

Flutter defines the `WEBRTC_` and `KRAKEN_` category constants and acknowledges `CREATE_CALL` and `CREATE_KRAKEN` (MT23, CL23). A call row is `not found` when no code uses those constants to do the call work.

## Implementation order

Cost is relative. **S**: isolated change in one module. **M**: several modules, or care with schema or protocol. **L**: a new subsystem with security-critical logic. **XL**: a new subsystem with native dependencies or funds at stake.

Most of what an assistant needs is already Done: sending and receiving the main message types, quotes, mentions on Signal text, group members, read receipts, recall, attachment upload and download, and disappearing message timers. The first two phases close the gaps around them.

| Phase | Scope | Rows | Cost | Main risk |
| --- | --- | --- | --- | --- |
| 0 | Make the workspace build: provide `protoc` | none | S | Without it nothing compiles here, so no later phase can be tested |
| 1 | Encryption and delivery correctness | E2E11, E2E06, E2E15, E2E17, MT17, GR19, E2E08, AT14, E2E09, E2E10, MT24, MT27 | M | Signal state regressions. Needs live validation with a real bot and two sessions |
| 2 | Assistant message features | MA03, MA06, MA04, MT12, MT09, EX02, EX07, MA08, MA09, AT12, AT13, PN01, PN03, MT21 | M | MA06 needs the right category choice for bot-addressed messages. PN01 retries can pin twice until the message id is stable |
| 3 | Members, contacts, conversations | GR08, GR21, CV04, CV10, US07, US10, CV18 | S | GR08 and CV04 differ from mobile request bodies and need a live check against the server |
| 4 | Remaining messaging and social | MT03, AT16, MT18, MT19, MT20, MT25, CV03, US08, US15, US19, SR10, SR13, ST01, ST03, ST11, NT09, NT10, NT14, NT15, NT16, NT17, NT20 | M to L | AT16 video transcoding brings a codec dependency. Notification actions need work on three platforms |
| 5 | Account settings, backup, bots without funds | SE, BK, and BT rows that do not need PIN | M to L | `POST me/preferences` is not implemented, which blocks privacy and currency writes. Bot OAuth widens what third parties can do |
| 6 | PIN and TIP | TP | L | Mishandling PIN, seeds, or the TIP counter can lock an account. Needs the native TIP library or a port |
| 7 | Safe wallet and transfers | WL, MT18, MT19, BT05, BT28 | XL | Handles funds. Needs Kernel transaction signing, bound from Go or ported to Rust, plus new output and raw transaction tables. Depends on phase 6 |
| 8 | Calls and voice rooms | CL | XL | WebRTC builds for each platform and frame encryption hooks. Group calls use Signal sender keys for media (CL15). No linked-device call rule was found in mobile code (CL24) |
| 9 | Other money products | W3 | XL | Many independent products with chain signing and imported key handling |

Phases 0 to 3 are implemented on branch `base-client-parity`, except AT13 (iOS-only bulk media recovery, which depends on a recovery protocol the fork lacks) and the US10 settings screen. None of it has been validated against a live account yet.

### Rows proposed for exclusion

These rows stay Missing in the tables until a decision is made.

| Rows | Reason |
| --- | --- |
| AC01 to AC07, AC15 to AC19, AC21 | Primary-device flows. This client signs in as a linked device by QR code. They become reachable only if the client can act as a primary device, which needs phase 6 |
| AC09 | Mobile manages desktop sessions from the primary device |
| AC24, NT01 to NT03, CL10 (VoIP push part) | Mobile push. A long-lived Blaze connection replaces it on desktop |
| SE07, US08 | Phone address book |
| BK03, BK09, BK10 | Phone to phone migration and mobile backup formats |
| MS10 | Both mobile apps have no home screen widget code to match |
| CL12 | Mobile permission flow |
| WL28, WL39 | Legacy wallet flows |
| W3 except W313, and W314 | Separate products; W314 is in-app purchase |
